# SGML2SQLへの実装依頼：相互作用相手の構造化・YJコード解決とOQSDrug連携

作成日：2026-09-22  
対象：SGML2SQL / OQSDrug  
状態：実装依頼・連携仕様案（以下の新テーブル・状態は未実装）

## 1. 目的と実装範囲

SGML2SQL側で、添付文書の相互作用相手を構造化し、相手薬のYJコード先頭7桁と対応付ける。OQSDrugではその対応表を使用して、電子カルテからCOMで取得した当日処方Aと、資格確認XMLから取得した他院薬Bを双方向に照合する。

この文書に基づき、SGML2SQLの抽出処理、解決処理、DBスキーマ、テスト、利用手順を実装してほしい。OQSDrug側の変更は別作業とし、接続仕様・サンプルSQL・データ例を引き渡すこと。本番データの再生成・公開は、検証結果と移行手順を確認した後の運用作業とする。

重い解析・辞書照合は取り込み時に行い、患者ごとのチェック時はコード照合を中心にする。未解決や分類候補を、確定したコード対応や「相互作用なし」と混同しない。

## 2. OQSDrugの現状

- `drug_contraindication`のレセ電コードを正逆両方向で照合している。
- `drug_code_map`と`sgml_rawdata`からYJコード・販売名・一般名を補っている。
- Aの`partner_name_ja`をBの名称に、Bの`partner_name_ja`をAの名称に照合している。
- XML由来とSGML由来の一般名を両方保持し、名称の双方向部分一致に対応済み。
- 相互作用行は自薬YJ先頭7桁でまとめて参照している。
- 名称照合は双方4文字以上を対象にし、「除く」「以外」を含む相手記載は行全体を除外している。これらは暫定的な候補抽出の制約であり、新しい抽出仕様の要件ではない。
- `standard_name_ja`の照合、薬効分類による候補展開、新しいコード対応テーブルの利用は未実装。

## 3. 確認済みの問題と調査対象

### 3.1 区切りなしの薬剤名連結

提供された`sgml_interaction.csv`に次の記載がある。

```text
エフェドリン塩酸塩dl-メチルエフェドリン塩酸塩フェキソフェナジン塩酸塩・塩酸プソイドエフェドリン
```

文字列だけから復元する前に、元XMLのリスト・改行・要素境界を確認すること。個別薬剤の列挙と配合剤の名称を区別する。中黒、空白、ハイフンを一律に薬剤の区切りとみなさない。

### 3.2 グループ名と個別名の対応

同じYJコード`5200138C1045`の複数行で、`partner_group_ja`が「マオウ含有製剤」のまま、相手名が次のようになっている。

- 葛根湯小青竜湯麻黄湯
- セレギリン塩酸塩ラサギリンメシル酸塩
- チロキシンリオチロニン
- テオフィリンジプロフィリン

抽出された見出しと個別名の対応に問題がある可能性がある。原因はまだ元XMLで確定していないため、該当文書を確認して修正・回帰テストを行うこと。現在の`partner_group_ja`を、そのまま群と成分の正解辞書にしないこと。

### 3.3 現行コードの確認箇所

確認したリビジョン：`696b5d05dd26f33d22a5fcd7ec4fb89752871b64`。実装時は最新コードとの差分も確認すること。

- [21_sgml2rawdata.py](https://github.com/YUKI-ENT/SGML2SQL/blob/696b5d05dd26f33d22a5fcd7ec4fb89752871b64/21_sgml2rawdata.py)：`lang_text_all`の空文字による`itertext()`結合、`extract_partner_group_and_items`の最初の`DrugName/Detail`を代表グループとして採用する処理。
- [22_build_sgml_interaction.py](https://github.com/YUKI-ENT/SGML2SQL/blob/696b5d05dd26f33d22a5fcd7ec4fb89752871b64/22_build_sgml_interaction.py)：`interactions_flat`からの転記と、`DROP TABLE ... CASCADE`による毎回の再生成。

### 3.4 提供サンプルの限界

参考ファイルは`sgml_interaction.csv`（100行）と`sgml_rawdata (2).csv`（500行）。後者は薬効分類49種類（NULL除外）で、前者の相手名との単純部分一致は0件だった。このサンプルだけで分類照合の有効性や網羅性を評価しないこと。ファイルはリポジトリに同梱されているとは限らないため、必要な元XMLと評価用データを実装環境で確認すること。

## 4. 抽出処理の要件

1. 原文・元文書・元XML内の位置を保持し、正規化後の情報から出典へ戻れるようにする。
2. 群名、具体名、群の例示薬、列挙、配合剤、除外条件を構造に沿って抽出する。
3. 複数見出しや入れ子リストの適用範囲を守り、先頭の見出しを無関係な後続項目に流用しない。
4. 「等」「例えば」は原文から消さず、例示であることを保持する。群に例示薬がある場合は、例示薬だけで群を解決済みにしない。
5. 「除く」「以外」などの否定と、剤形・投与経路などの限定を保持する。除外された薬剤を肯定の対応として登録しない。
6. 解析不能な構造・条件は未解決として残し、誤った確定コード対応を生成しない。
7. 原文用の既存列と、検索・解決用に正規化した情報を分離する。

## 5. コード解決処理の要件

抽出とは独立した後処理として実装する。名称辞書・群辞書を更新した際に、元XMLの再取り込みなしで解決処理を再実行できる構成を目指す。

| 段階 | 解決方法 | 基本的な扱い |
| --- | --- | --- |
| 1 | 一般名・標準名・販売名の正規化一致 | 具体名の対応。適用条件も検証する |
| 2 | 確認済みの別名・表記ゆれ辞書 | 辞書の出典・版を付けた対応 |
| 3 | 部分一致などの名称検索 | 要確認候補。包含だけで確定しない |
| 4 | 原文の薬効群と分類・群辞書の照合 | 分類に基づく候補。検証済み辞書はその旨を記録 |
| 未解決 | コード・対象範囲を決定できない | 対象記載と理由を残す |

### 5.1 複数コードと曖昧さ

一つの具体名や群から複数の相手YJ先頭7桁が得られることを許容する。複数の正しい対象薬がある場合と、名称の曖昧さによる複数候補を区別する。YJ先頭7桁を成分の一意識別子と仮定しない。

### 5.2 薬効分類の使用

- 相互作用原文に記載された相手群と、対象薬の`therapeutic_class_ja`を照合する。
- 自薬と相手薬の薬効分類同士の類似を相互作用の根拠にしない。
- 具体名が未解決であることだけを理由に、同じ薬効分類の全薬へ広げない。
- `partner_group_ja`と`therapeutic_class_ja`を同一の分類体系として扱わない。
- 「抗てんかん剤／抗てんかん薬」などの表記ゆれは管理可能な同義語辞書で処理する。「剤」「薬」などの一律削除による意味の衝突を避ける。
- CYP阻害・誘導、特定成分含有などの群は薬効分類だけで推定せず、出典付きの専用辞書を使用する。対応情報がなければ未解決のまま残す。
- 部分一致で薬効分類が一致しただけの結果を、確認済みの対象薬として扱わない。

### 5.3 YJ先頭7桁の限界

主な検索キーは相手YJ先頭7桁とする。ただし、全桁コード・剤形・投与経路等の条件を7桁への集約で失わないこと。7桁の一致のみで適用できる対応と、追加条件の評価が必要な対応を機械的に区別する。

## 6. データモデル案

`sgml_interaction`に相手コードを一つだけ追加する方式ではなく、以下の1対多の関連テーブルを推奨する。列名は提案であり、変更する場合はOQSDrug向け契約を文書化すること。

```text
sgml_interaction（原文・自薬・区分・症状・機序）
  └─ sgml_interaction_target（抽出した相手記載：複数）
       └─ sgml_interaction_target_code（相手コードと根拠：複数）
```

### 6.1 sgml_interaction

既存の表示用列と意味を維持する。必要に応じて、元文書の版、抽出位置、安定キー、データ世代を追加する。既存OQSDrugが読む列を削除・改名しない。

### 6.2 sgml_interaction_target

| 列案 | 内容 |
| --- | --- |
| id | 主キー |
| interaction_id | `sgml_interaction.id`への外部キー |
| target_key | 原文と構造に基づく追跡用キー |
| parent_target_id | 群と例示薬などの親子関係。必要時のみ使用 |
| target_name | 抽出した相手名・群名 |
| normalized_name | 解決用の正規化名 |
| target_kind | `drug` / `group` / `unknown` |
| mention_role | `target` / `example` / `exclusion`など |
| resolution_status | `resolved` / `partial` / `unresolved` |
| condition_text | 除外・剤形・投与経路などの原文条件 |
| condition_status | `none` / `supported` / `unresolved` |
| unresolved_reason | 部分解決・未解決の理由 |
| source_locator | 文書内の節・XML位置・項目番号など |
| generation_id | データ世代 |

「シメチジンは解決済み、同じ相互作用行にある薬効群は未解決」という状態を表現できること。未解決を表すためだけのNULLコード行は作らず、対象記載側で管理する。

`resolved`は対象範囲の解決が完了した状態、`partial`は一部のみ解決、`unresolved`は確定できていない状態とする。候補コードが存在するだけでは`resolved`にしない。実装時に状態遷移・集計規則を確定し、テストすること。

### 6.3 sgml_interaction_target_code

| 列案 | 内容 |
| --- | --- |
| id | 主キー |
| target_id | `sgml_interaction_target.id`への外部キー |
| partner_yj7 | 相手YJ先頭7桁。必須 |
| match_method | `name_exact` / `alias_dictionary` / `name_partial` / `class_dictionary` / `class_text`など |
| evidence | 対応付けに使用した語句・分類・出典。JSONB等で構造化可能 |
| review_status | `accepted` / `needs_review` / `rejected` |
| applicability | `yj7_sufficient` / `requires_condition` |
| dictionary_version | 対応辞書の版 |
| resolver_version | 解決処理の版 |
| generation_id | データ世代 |

必要な場合は、許可する全桁YJコードや評価可能な条件を別の子テーブル等に保持する。自由記述の条件しかない対応を、7桁一致だけで採用しない。

`accepted`は対応付けが採用可能であることを示し、相互作用の重症度ではない。併用禁忌・併用注意は元の`section_type`を保持する。自動採用の条件と人手確認の有無も追跡可能にする。

同一コードへの複数の根拠を保持しつつ、単なる再実行による重複を防ぐ一意制約を設計する。外部キー列と`partner_yj7`に適切な索引を設ける。

## 7. 更新・公開と互換性

現行22番の`DROP TABLE ... CASCADE`をそのまま使うと、関連テーブルやOQSDrugとの整合性を損なう可能性がある。以下を満たす更新方式へ変更すること。

- 抽出・コード解決・整合性検証は公開中データとは別に実行する。
- 原文と関連テーブルを同一世代として、トランザクション等で一括公開する。失敗時は前の正常世代を参照し続けられるようにする。
- OQSDrugが複数クエリで取得しても世代が混ざらない、世代指定または読み取り手順を提供する。
- 再採番された`id`を、前世代のコード対応やレビュー結果に流用しない。
- 再生成しても追跡できるキーと原文・条件のハッシュを設計する。文書改訂や条件変更時に古い確認済み結果を無条件で引き継がない。
- 同じ入力・辞書・プログラム版での再実行は、内容が同じ結果となり、重複・古い対応が残らない。
- スキーマ版、公開世代、生成日時、元データ版、辞書版、解決処理版を取得できるようにする。
- 既存の表示機能・権限・索引・依存ビュー等の互換性を確認する。
- バックアップ、移行、失敗時復旧の手順を用意する。

## 8. OQSDrugとの接続契約

SGML2SQL側は以下を含むサンプルSQLまたは参照ビューを提供すること。

1. 自薬YJから相互作用と相手コードをまとめて取得する方法。
2. 相手YJ先頭7桁の一致で検索する方法。
3. 原文・区分・症状・機序・照合方法・根拠・条件・解決状態を取得する方法。
4. 未解決の相手記載と、未解決件数を取得する方法。
5. データ世代とスキーマ版を確認する方法。

OQSDrug側はAの相互作用→BとBの相互作用→Aを照合する。`needs_review`は候補として区別し、`rejected`・除外対象を肯定結果に含めない。条件未評価の対応は確定結果として扱わない。

当面の移行時には新テーブルがない環境で既存の名称照合を継続できるようにする。新テーブルがある場合の名称照合は未解決部分の補助とし、明示的な除外・却下を打ち消して復活させない。原文と対応キーにより重複表示を抑える。これらのOQSDrug側変更は別途実装する。

自薬側も全桁コードと先頭7桁のどちらを適用単位とするかを仕様化する。現在の7桁集約を無条件に新仕様へ引き継がない。

## 9. テストと受け入れ条件

元XMLの小さなフィクスチャを用意し、抽出とコード解決を独立してテストする。本番DBへの接続なしで基本の回帰テストを実行可能にする。

| ケース | 期待結果 |
| --- | --- |
| シメチジンの具体名 | 一般名辞書から該当するコード集合を得る |
| 区切りなしに見えていた列挙 | 元XMLの境界に沿って抽出し、配合剤と区別する |
| 複数見出し・入れ子リスト | 見出しと個別名が正しく対応する |
| マオウ含有製剤の提示例 | 元XMLで確認した正しい抽出を固定する |
| 群＋例示薬 | 群を残し、例示薬の解決だけで群全体を完了解決扱いしない |
| 部分解決 | 解決できた相手と未解決の相手を両方保持する |
| 除外・括弧外の「以外」 | 除外対象が肯定のコード対応にならない |
| 薬効分類のみの候補 | 具体名一致と異なる方法・確認状態で保存する |
| 無関係な薬剤・短い断片 | 不適切な確定対応を生成しない |
| 複数YJ・規格・経路条件 | 多対多の対応と適用条件を維持する |
| 再実行・文書改訂 | 重複や古い対応が残らず、確認結果の誤継承がない |
| 公開途中の失敗 | 旧世代を利用可能で、関連の孤立・世代混在がない |
| 既存OQSDrugとの互換性 | 既存列の参照と原文表示を継続できる |

評価レポートには相互作用行数、対象記載数、解決済み・部分解決・未解決数、候補数、除外・条件未解決数、解決方法別の件数、前世代との差分を含める。レビューしたサンプルの誤対応・見落としも報告する。件数増加だけを改善の指標にしない。

## 10. 実装順序と引き渡し成果物

### 第1段階：抽出修正と具体名の解決

- 該当元XMLの調査、境界・グループ対応の修正。
- 関連テーブルと状態・世代管理の導入。
- 一般名・標準名・販売名と確認済み別名からのコード解決。
- 回帰テスト、移行手順、OQSDrug向け参照例。

### 第2段階：薬効群の候補展開

- 同義語・群と成分の対応辞書を出典付きで追加。
- 薬効分類からの候補生成と確認手順。
- 除外・適用条件に対応できないものは未解決として保持。
- 検出範囲・誤対応・見落としの評価。

### 引き渡し時に必要なもの

- 変更したスクリプト、DDL・移行スクリプト、テスト。
- 実際のテーブル・列・状態値を記した連携仕様。
- 具体名一致、分類候補、部分解決、未解決、除外条件のデータ例。
- OQSDrugで使うサンプルSQLと、索引・取得単位の説明。
- 検証結果、既知の制約、実データ再生成・公開・復旧の手順。

不明なXML構造や分類の対応を推測で確定せず、未解決理由として可視化すること。まず第1段階を完成させ、OQSDrug側が連携実装できる契約を確定してから、第2段階を拡張する。
