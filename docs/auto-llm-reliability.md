# 自動LLM問い合わせの待機・再試行

2026-09-18

## 自動送信の起動条件（2026-11-10確認）

- テンプレートの「自動取得」をチェックして保存する。
- 薬歴を取り込むPCで、設定の「AI自動検索」を有効にして保存する。設定はPC側のユーザー設定であり、テンプレート側のauto_fetchとは別。
- PostgreSQL使用時に、resフォルダのYZK薬歴XMLを取り込んで成功したときに患者キューへ依頼する。テンプレート保存や患者画面の表示だけでは起動しない。デバッグ用の手動XML取り込みも現在は起動対象外。
- 同一患者・同一タイトルで直近1日以内に本文のある成功結果がある場合はスキップする。手動送信の成功結果も対象。テンプレートの修正やモデル変更だけでは、このスキップ条件は解除されない。
- 同じ患者がキュー待ち・実行中なら依頼を統合する。患者キューとLLM送信は直列なので、先の処理・再試行が長いと待機する。
- `[AutoFetch]` ログの「取込後判定」「起動スキップ」「キュー受付」「キュー処理開始」「自動取得テンプレート数」、テンプレート別のskip／failed／done、完了件数でどこまで進んだか確認する。

## 修正した取りこぼし

- 別患者の自動問い合わせ実行中に、新規依頼をSemaphoreSlim.WaitAsync(0)で破棄していた。患者単位のFIFOキューへ変更し、処理中・待機中の同一患者はまとめる。
- エラーやpendingの履歴も「1日以内の実行済み」に含めていた。本文のあるsuccessだけを対象とする。失敗した依頼は次の薬歴取得時に再度対象になる。
- 1つのテンプレートが失敗すると、残りのテンプレートも実行されなかった。テンプレート単位で例外を扱い、残りを続行する。

## 再試行

自動送信だけ、HTTP 408・429・502・503・504、通信例外、タイムアウトを初回を含め最大3回試行する。待機は15秒、45秒。Retry-Afterがあればその時間を優先する。認証エラー・モデル名不正等の恒久的なHTTPエラーや応答形式不正は再試行しない。

1回の自動送信のタイムアウトは設定値と300秒の大きい方。手動送信は従来の設定値のまま。再試行中も同じai_resultsのpendingレコードを使い、最終結果をsuccess/errorとして保存する。空本文は成功としない。

待機・通信はバックグラウンドで行う。自動問い合わせのログに再試行理由、成功・スキップ・失敗件数を記録する。

## 範囲と制約

- 待機キューはメモリ上にあり、アプリ終了・再起動をまたぐ再開は未実装。
- タイムアウト時はサーバー側で実行済みか確定できず、再試行で推論が重複する可能性がある。DB結果は同じ依頼レコードへ保存する。
- 再試行上限に達した後はエラーを記録し、次のテンプレート・患者へ進む。
- 実LLMサーバーへの送信・実DBを使う検証は未実施。

## 検証

`tests/Run-AutoLlmTests.ps1`でFIFO、混雑中の保持、同一患者の重複抑止、患者処理失敗後の続行・再受付、一時エラーからの回復、恒久エラー、再試行上限、Retry-After、キャンセルを検証。

## 空応答の診断（2026-11-10）

- テンプレートの「thinkingを無効」は、Ollamaの `/v1/chat/completions` に `reasoning_effort: "none"` を送る。`thinking: false` は送らない。
- 手動・自動とも既存のログファイルに `[LLM rid=...]` でリクエスト設定と応答概要を記録する。設定したモデル・制限時間・無効化指定、HTTP状態、経過時間、Content-Type、応答文字数、JSONの状態、choices件数、finish_reason、回答・思考の文字数、トークン数を確認できる。
- HTTPボディが空、JSON不正、回答フィールド欠落、回答が空を区別する。JSONはあるがcontentが空でreasoningCharsが大きい場合は思考のみの応答を疑い、finish_reasonがlengthなら生成上限も確認する。応答概要には回答本文・思考本文を含めない。
- `tests/Run-LlmResponseTests.ps1` は署名を無効にした検証用ビルドを作り、ローカル模擬APIへの送信指定と応答解析・診断情報を検証する。実Ollamaでの結果は別途ログで確認する。
